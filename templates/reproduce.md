# 课题标题

> 论文复现：拿一篇已发表的论文，用它自己的代码（或别人的实现）把它报的数跑出来。复现不是改进——目标是「数对上」和「对不上时说清差在哪」，不是把数做得更好。四样说清楚：哪篇、哪几个数、复现到第几级、对上的标准。

## 论文

待填：题目、链接（arXiv / DOI）、发表年份；它的主要主张是什么；研究者为什么要复现它（校准自己的评测、学习方法、当自己工作的基线）。

## 要复现的数

待填：论文的哪张表、哪几行、哪几个指标（写论文报的原值）；不复现的部分也写明（比如需要人的实验、要几百 GPU 小时的表）。

## 复现到第几级

待填：一级——官方代码 + 官方数据原样重跑（证明结果可重跑）；二级——换实现（第三方仓库）、换机器、换种子（证明结果不依赖某台机器某个种子）；三级——只照论文描述重写（证明论文写清楚了）。选一级并说明为什么。

## 材料

待填：官方代码仓库（链接、要用的 commit 或 tag）、数据（在哪、多大、许可）、预训练权重、别人的复现、复现报告里已知的坑；`materials/` 里已经拉下来了哪些（`download` 的收据）；还缺什么、谁去补。

## 怎么算对上

待填：主指标与论文值差距在多少以内算对上（论文给了误差棒就按它的；没给就研究者定，比如相对差 5% 以内）；跑几次、报中位数还是均值；哪些差异可以接受（换 GPU 型号引起的第三位小数漂移）、哪些不行。

## 算力、环境与预算

待填：跑一次要多久、要不要 GPU、要哪些 API key 或账号（写名字不写值，值放起服务的环境里）；用机器上现成的环境还是按仓库的 requirements 新建；总时间与花费上限；哪一步要人确认。

## 交付

待填：一份复现性分析（论文值 vs 我们的值、差在哪、为什么）、能重跑的评分脚本、改过的代码的 diff。
